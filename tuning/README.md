## How to change something

1. Open the page in any text editor (Notepad is fine). The game can keep running.
2. Change the number after the `=`. Leave the name before the `=` and the `[section]` lines as they are.
3. Save. Within half a second the game plays on with the new number. In co-op the host's pages are the ones that count: the host's game sends them to everyone, and every player switches on the same tick.

A few numbers only take effect at the next start, because they set up the match: the top of the player HP bar (max HP) and where the players start. (The floor and the camera are rebuilt on a save, the ring arena too: its shape, pillars and vents follow a save of the volcano page; a broken pillar keeps its countdown.) On the boons page, a boon's effect (Dagger's speed, Vampire amulet's heal) changes at once for everyone holding it; the meter's rates, the cap, `claim_radius_m` and `approach_radius_m` at once; the rest of `[racks]` (type weights, offer sizes, spacing, margins, rise time) from the next rack that appears.

### Or with the tuning screen

In a developer build (`play.cmd`, or a run from the Godot editor), the host or a solo player can press **Tune** in the co-op lobby or the solo pick, or **Tune (T)** on the death screen. It edits these same pages: every value is listed by subject (a tab per character, grouped as he plays: Light, Heavy, each combo with its ender and chaining values, Ultimate, Defence, Look; then Enemies, Boons, Zone and progression, Shared, Global), with the comment above it as help and its page and name in small print; − / + and the typed value stay inside the range the game accepts. **Apply** writes the staged values into the pages, changing only the value after the `=` on each line (comments, blank lines and order stay), and the game picks them up as it does a save from a text editor. A value the game would refuse is not written; the screen names it. Each applied change goes on a line in `logs/tuning-changes.txt` (time, page, `[section] key`, old -> new). The orange dot and **Reset** compare with the pages as committed in git. Which page a tab reads: a character's tab reads his own page (`mage.cfg`, `duelist.cfg`, with the mage's hit-stop and knockback from `feel.cfg`); its Light group is the `[<id>.move.light]` section and its **Hit 2** / **Hit 3** rows are the override lines of `light_2` / `light_3`, whose **Same as Light** deletes that line on Apply. Shared reads `character.cfg`, `camera-and-arena.cfg` and `feel.cfg`; Zone and progression the zone pages (the arrival batch included); Global reads `global.cfg`, a multiplier not at 100 orange, the tab titled "Global (N changed)". See PLAYING.md, "Change the numbers".

Before tuning a move's frames or windows, read `docs/combat-pace.md`: P-O's pace direction (fast, flowing basics; weight from impact; a few big moves committed but short), every move's frames today and what each move can cancel into.

Change one number at a time and write down the old value first. The pages are kept in git, so a bad tuning session can always be rolled back.

## Bake the Global tab in

When P-O says a tuning pass is good, Code folds the Global multipliers into the single values and sets them back to 100 (GLOSSARY: Bake-in), headless, from the repo root:

1. Run the suite (`./run-tests.ps1`) and note that the golden replays pass: they are the digests the bake must keep.
2. `powershell -ExecutionPolicy Bypass -File tools/bake_in.ps1 --dry-run` shows what would move: for each multiplier not at 100, every page key of its category (the table in `global.cfg`'s row above, `GlobalMultipliers.category_of`), the values the rounding moved off the exact product, and a fixed-seed run's digest before and after.
3. `powershell -ExecutionPolicy Bypass -File tools/bake_in.ps1` writes it: each key times its multiplier, rounded as loading rounds, only the value after the `=` changing; every multiplier back to 100. It writes nothing unless the proof holds: the resolved tuning equal key by key to the one with the multipliers applied, and the same fixed-seed run digest. Any rounding it reports goes to P-O with the keys involved. (`--folder=<path>` bakes another tuning folder.)
4. Run the suite again: the golden replays must be unchanged.
5. Commit the pages with the message the tool prints (each multiplier and the keys it touched), and report the hash.

## If a number is refused

A missing value, a typo, text where a number belongs, or a number outside its range is refused with a message naming the page and the value, for example `camera-and-arena.cfg: [camera] height_m must be a number, got "six"`. Saved while playing, the game keeps the last good numbers and shows the message in red on screen until you fix the line and save again. Already wrong when the game starts, it stops the game with the message; fix that line and start again.

A character's light swings share one **Light group**: `[mage.move.light]` (with the mage's hit-stop and knockback in `feel.cfg`'s `[move.light]`) and `[duelist.move.light]` hold every light-swing value. Each swing's own section (`light_1`, `light_2`, `light_3`) holds its chaining values (its combo window and next moves: the combo graph) and only the values where it differs, its overrides: change a Light value and every swing without an override for it changes; delete an override's line and that swing follows Light again. The mage's third hit overrides its speed, windows, reach, arc, step, hit tier, damage, hit-stop and knockback, his second its recovery and dodge window; the Duelist's strikes override nothing.

A few rules the pages follow:

- A comment line starts with `;` (not `#`).
- Whole numbers have no decimal point (`5`, not `5.5`).
- A word value goes in quotes (`hit_tier = "flinch"`, not `hit_tier = flinch`); its comment lists the words it accepts.
- A colour goes in quotes as a colour code: `"#"` then red, green and blue as two hex digits each, `00` to `ff` (`telegraph_color = "#ff4a1c"`, `lane_color = "#ff5a1f"`).
- A boon's `effect` is the sentence shown under its name when you grab it. Write it in your own words; a value's name in braces, like `{light_swing_speed_percent}`, shows that boon's value there, so the sentence stays true when you change the number. Only the boon's own values can go in braces (a misspelt one is refused, naming the boon). A whole number right before `st`, `nd`, `rd` or `th` gets the one that reads right (`{every_nth_light_hit}rd` shows 3rd, 4th, 21st...). Held twice or more, the total follows on its own line, from the first value that adds up to the end of the sentence ("x2: 20% faster").
- Each value lives on exactly one page. Writing it on another page, or misspelling its name, is refused rather than silently ignored.

## Units

- **m**: metres. The player is about 2 m tall.
- **m/s**: metres per second.
- **deg**: degrees. 360 is a full circle.
- **frames**: simulation ticks. The game runs at a fixed 60 per second, so 60 frames is one second and 6 is a tenth of a second.
- **pixels**: screen pixels (the outline's width stays the same near or far).
- **seconds**: real time, for looks only (how long a shockwave or the cracks take to fade); everything that plays is in frames.
- **frame number**: a position inside a move, counting the move's first frame as 1.
